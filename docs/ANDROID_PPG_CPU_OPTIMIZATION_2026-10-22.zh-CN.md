# PPG-AN00 CPU 侧优化与 60 FPS 调查（2026-10-22）

设备：PPG-AN00（骁龙 8 Elite / Adreno 830，Android 17），系统驱动，营地场景，渲染比例 1.0（100% 画面），已解锁出图节拍（`present-60fps`）。
**测量条件的重要说明**：全部测量时电量 12%–45%，系统把 CPU 频率封顶：中大核 `scaling_max=2.23 GHz`（硬件 3.53 GHz），超大核 cpu6/7 被锁死在 1.02 GHz（硬件 4.47 GHz）。绝对 FPS 在满电、低温时会更高，下面的**相对提升**才是可迁移的结论。

## 结论

营地场景 36 → 约 45 FPS（累计），画面不变，没有降低任何画质。离 60 FPS 还差约 25%，在降频状态下做不到；在满频下可能做到（见最后一节）。

## 瓶颈在哪里

- 不是 GPU：渲染比例 1.0 与 0.70 帧率相同，GPU 每帧只忙约 13 ms。
- 是 CPU，而且是两个线程**串行**工作：游戏每帧提交后连续调用 21 次 `nvnDeviceFinalizeCommandHandle`，每次都排空翻译队列，所以帧时间 ≈ 游戏线程（约 9.7 ms）+ 回放线程 `nvn-translate`（约 13 ms）。游戏线程 62% 的时间在 futex 里等回放线程。
- 不排空、让两边重叠（`finalize-wait.txt=none`、`acquire-sync.txt=early`）反而慢约 7%：游戏线程能提前最多三帧，但回放线程的墙钟时间涨到约 20 ms，周期数不变（≈ 31.7 Mcycles/帧），等价于运行频率更低。绑核（回放线程 cpu7、游戏线程 cpu6）没有改善，ADPF 提示也没有。因此默认保持串行。

## 已落地（均有 A/B，默认开启，各带关闭开关）

## 试过、不采用

- `finalize-wait=none` / `ticket`、`acquire-sync=early`：见上，更慢。
- ADPF 性能提示（目标 16.7 ms）、回放线程绑超大核：无变化。
- 动态 UBO 在系统驱动上（`enable-dynamic-ubo`）：描述符命中率 30% → 75%（再放宽非升序绑定到 89%），但回放线程总 CPU 不变，FPS 不变；保持关闭，仅留开关。
- GPU 回写（`commit_after_gpu` 约占全部采样 2.9%，回放线程的 6%）：每帧约 8 个范围、2.4 MB，主要是主数据池（744 MB）里一个 1 MB 和一个 1.3 MB 的 GPU 计算输出。要跳过它们必须能检测"游戏是否会读这些页"，读到时还要当场同步回读 GPU 数据，而这得在 SIGSEGV 处理函数里调 Vulkan，不可行；因此不做。
- 控制块的脏页戳：控制块不在被追踪的池里（0 / 200000），且需保留字节校验。
- 跳过全部 UI 方块（664 draw/帧）上界只有 +8%：UI 快路径每个 draw 约 2.7 µs，已经很便宜。
- 逐 draw GPU 时间戳在这个驱动上粒度太粗（约 1 µs），PPG 上不可用于排序。

## 第二批：脏页追踪的内核开销（最大的一项）

用户态采样（`cpu-cycles:u`）完全看不到内核时间。加了 `DIRTY_COST` 计数后发现：营地每帧约 **420 次写保护缺页、840 次 `mprotect`，`mprotect` 本身耗时约 9 ms/帧**（串行模式），重叠模式涨到 15.7 ms/帧，因为游戏线程的缺页处理和回放线程的重新保护抢同一把进程内存锁——这就是前一批里"重叠模式反而更慢"的真正原因。

机制：池页面被回放读取后写保护；游戏再写就缺页，处理函数逐页解保护并标脏；下次读取时重新上传并重新保护。

改法（`nvn_dirty.c`，默认开启，窗口 64 KB = 16 KB 页上 4 页，4 KB 页上 16 页）：

- **缺页合并**：缺页时把同一对齐窗口里相邻、处于保护状态的页一起用一次 `mprotect` 解保护并标脏。
- **保护对齐**：`nvn_dirty_protect` 把要保护的范围对齐到同样的窗口，相邻的小范围合并成一次调用。
- 两个方向都只会**多标脏 / 多保护**，不可能漏掉写入：多标脏的邻页下次读取时重新上传；多保护的页只是以后多一次缺页。

| 窗口 | FPS | 缺页/60 帧 | `mprotect` 耗时/60 帧 |
| --- | ---: | ---: | ---: |
| 关闭（1 页） | 43.3 | 25.5k | 490 ms |
| 2 页 | 47.7 | 17.9k | 305 ms |
| 4 页（默认） | 48.0 | 10.7k | 179 ms |
| 8 页 | 43.0 | 5.8k | 166 ms |
| 16 页 | 38.7 | 3.3k | 141 ms |

更大的窗口缺页更少，但多标脏导致多上传，反而变慢。默认值下配对测试（同一状态、交替）：36.7 → 45.4 FPS（+24%）。

验证：营地截图与基线的差异等于基线对基线的噪声（均值 0.45–0.56）；120 秒、7210 帧走动 + 开关菜单 0 个异常帧、0 个错误；"保存并退出 → 选角 → 重新进入"（覆盖池的销毁与重建）正常；新增 `t_dirty_around` 测试（窗口认领、邻页、边界、池末尾），已有的精确语义测试在窗口=1 下运行，`dirty-race`（4 个写线程同时缺页）在窗口 4/8/16 下也通过。关闭方式：`diagnostics/disable-fault-around` 或 `fault-around.txt` / `protect-around.txt`（页数，1 = 精确）。

## 重叠模式（游戏线程与回放线程并行）的重新评估

`mprotect` 争用消除之后，`finalize-wait.txt=none` 与串行持平（45.4 vs 45.6）但没有更快。现在回放线程每帧要**等 GPU 约 7.5 ms**：渲染只有一个提交槽，复用槽前必须等上一帧的 GPU 工作完成，而一帧的 GPU 尾巴（最后几道后处理）不能提前。要继续往上，需要第二个渲染提交槽 + 池数据多版本化，是之前已确认数据竞争风险最高的方向（37 次/帧真实冲突），这里没有尝试。

## 稳定性

120 秒（7210 帧）营地走动 + 开关菜单：0 个异常帧、0 个错误、进程存活。TNA（Turnip）**没有重测**这批改动，下次接上 TNA 需要回归（`storage_bias` 修复、描述符复用、着色器缓存对所有驱动生效）。

## 诊断工具

`guest-wait-diag[=trace]`：游戏线程等待分解、`THREAD_RUSAGE`、`NVN_CALLS`、`FINALIZE_HANDLE`、`SYNC_TRACE`；`desc-diag`：描述符 miss 归因；`draw-timing`；`wsi-diag`。`analysis/perf-runs/ppg-1022/run-world.sh <label> [标记...]` 一键进入世界并输出最后几个 60 帧窗口。

## 测量与回归工具（`tools/android/`）

| 脚本 | 用途 |
| --- | --- |
| `perf_run_world.sh <标签> [标记[=值] ...]` | 清掉所有实验标记，冷启动，按屏幕比例点击"进入游戏"，打印最后几个 60 帧窗口的 FPS（`ENTER=gamepad` 或 `ENTER="tap X Y"` 可改进入方式；日志写在脚本目录） |
| `perf_bench_all.sh [轮数]` | 本批全部优化关闭 vs 默认的累计对比，每轮打印电量和频率上限；电量低于约 60% 时给出警告 |
| `perf_regress.sh [轮数]` | 换设备（如 TNA / Turnip）回归：全开 vs 逐项关闭，每次都统计日志里的错误，最后对比"全关"与"全开"的截图差异 |
| `perf_glitch_scan.py <mp4...>` | 在录屏里找孤立的异常帧（闪烁 / 转置帧） |

这些脚本依赖 `android_d2r_apk.py --debuggable` 打出的调试版 APK（`run-as` 读日志、写标记）。
