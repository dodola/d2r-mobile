设备 TNA-AN00（Adreno 642L，60 Hz），系统驱动，100% 画质，角色选择场景，冷机（Thermal Status 0）。

### 已验证无效或不可行

| 尝试 | 结果 |
| --- | --- |
| 合并头发/模型 pass | 不存在可合并的两个 pass；纹理 transition（L1502）一次也未触发 |
| 深度 `EQUAL` 改 `GREATER_OR_EQUAL`（启用 LRZ） | 片元调用增加约 30%，说明彩色 pass 有约 25% 片元比 prepass 深度更近，画面会改变，不可用 |
| 纹理 LOD bias +4 | 彩色 pass 仅快约 10%，纹理带宽不是主因 |
| `spirv-opt -O` | 着色器几乎不变，耗时无变化 |
| `--relax-float-ops`（fp16） | 耗时无变化 |
| 去掉 1354 条 `NoContraction` | 耗时无变化 |

Eden 的着色器路径同样没有快速数学开关，最终优化交给驱动编译器，结论一致。

## 根因：渲染段共用一个槽位

所有渲染段都使用 `G.submission_slot`，present 单独使用 `submission_slot2`。第 N+1 段开始录制前必须等第 N 段在 GPU 上
完成并发布，CPU 与 GPU 因此串行（约 42 ms + 42 ms ≈ 84 ms）。

## 修改

- `nvn_vk.c`：渲染段改为环形槽位。数量由 `DM_RENDER_SLOTS` 决定（1 到 4，**默认 1，即原行为**）；额外槽位自行分配命令池和描述符内存。
- 每个提交开头加入一个全局内存屏障（`ALL_COMMANDS` 到 `ALL_COMMANDS`），保证后一帧等待前一帧的 GPU 写入。槽数为 1 时不加。
- `app_jni.c`：`diagnostics/render-slots.txt` 标记文件，内容为槽数；删除后使用默认值。
- 新增诊断（默认关闭）：PASSLOG 中每个 pass 的深度测试/写入/比较函数、模板配置和深度附件 load/store 操作；
  `lod-bias.txt`、`dump-shaders`、`shader-override/`（用离线 SPIR-V 覆盖指定着色器）。

## 结果（交错重复测量）

| 渲染槽数 | FPS |
| ---: | ---: |
| 1（原行为，重复 3 次） | 11.9 / 11.9 / 11.9 |
| 2 | 14.75 |
| 3 | 14.70 |

彩色 pass 耗时不变（约 2299 ms / 60 帧），属于纯流水线收益。2 槽后 GPU 受限（61.6 ms GPU，67.8 ms 帧时间），3 槽没有额外收益。
注意：设备过热时单次测量会偏低（出现过一次 9.4 FPS 的瞬态），对比必须交错重复。

## 更正：2 槽的 +24% 来自数据竞争，不能采用

随后加入页级冲突检测（每个 pool 为每个渲染槽记录 4 KiB/256 B 的读写位图；CPU 写镜像前若与其他在途槽位重叠，等待其 GPU fence，并计数）。

| 粒度 | 每 60 帧冲突数 | 2 槽 FPS |
| --- | ---: | ---: |
| 无检测（旧实现） | 未知 | 14.75 |
| 4 KiB 页 | 约 3200（约 53/帧） | 12.3 |
| 256 B | 约 2200（约 37/帧） | 11.7 |

粒度缩小后大部分冲突仍在，说明是真冲突：游戏在帧 N 的 GPU 仍在读取的同一段缓冲上写入帧 N+1 的数据。加冲突等待后 2 槽没有收益，
所以此前的 14.75 FPS 是靠 CPU 与 GPU 同时访问同一镜像换来的，不安全。这与历史记录“未版本化的双渲染上下文已排除”一致。
要安全重叠需要按帧版本化动态缓冲（每槽独立镜像或 GPU 有序暂存上传），之前的暂存上传尝试因每帧约 750 次上传导致帧率崩溃，改动面很大。

结论：渲染槽保持默认 1，多槽仅在带冲突检测的前提下可用，日志 `RENDER_SLOT_PROFILE conflicts=` 给出冲突计数。

## 渲染比例实测（单槽，系统驱动）

| 渲染比例 | FPS |
| --- | ---: |
| 100% | 约 12.4 |
| 90% | 约 13.4 |
| 75% | 约 15.2 |

75% 的像素数只有 100% 的 56%，帧率仅提高约 22%：单槽时帧时间约等于 CPU（约 42 ms）加 GPU，分辨率只影响 GPU 那一半。
因此 CPU 回放仍是主要杠杆。用户已确认中端设备可以默认使用 0.75 档。

## 验证状态与风险（默认保持 1 槽的原因）

- 角色选择场景：1 槽与 2 槽截图一致，无花屏或闪烁；日志无 FATAL、VK_ERROR 或 DEVICE_LOST；持续数分钟稳定。
- 未验证：进入游戏世界后的战斗、地图切换、存档。adb 注入的点击无法可靠进入游戏世界，需要手动验证。
- **数据竞争风险：** 多槽意味着帧 N+1 的 CPU 录制、pool 镜像刷新与仍在 GPU 上执行的帧 N 重叠。对严格遵守 NVN 栅栏的游戏理论上安全，但历史记录里“未做版本化的双渲染上下文”曾被排除，这里没有证据证明它在战斗、地图切换、存档中安全，因此默认不启用。
- 启用方式（需先在游戏内验证）：`adb shell run-as org.d2r.newprobe sh -c "printf 2 > files/d2r-mobile/diagnostics/render-slots.txt"`，退回删除该文件。
- 如果游戏内出现闪烁、贴图错乱或闪退，先写入 `render-slots.txt` 内容 `1` 退回原行为，再对比。

## 渲染正确性：系统驱动的雾气伪影（未解决，已定位到 pass 008）

角色选择场景里，系统 Adreno 驱动会画出块状白色马赛克（雾气区域），Turnip 上没有。量化指标：裁剪区内亮度大于 120 的像素占比，系统驱动 5–13%，Turnip 约 0.55%。

**排除项**（开关打开后伪影仍在）：存储省略、清除合并、`subres`、采样拷贝缓存、资源缓存、描述符缓存、屏障省略、`storage-bias`、`temp-pool`、`wait-elision`、`wb-stage`、`async-commit`、`dirty-uploads`、`cpu-uniform-snapshot`、`command-state-cache`、`driver-table-reuse`、`control-cache`；跳过 12 个热点像素着色器；`precise-sync` 关闭时变成随机彩色噪点（说明读到未定义数据）。深度比较采样器对 D16 阴影图改用最近邻也没有效果（该改动已撤回）。

**定位方法**：`diagnostics/dump-frame.txt` 写入帧号 N，每个颜色/深度 pass 结束后把第一个附件拷贝到诊断目录 `pass-<序号>-<宽>x<高>-fmt<格式>-bpp<n>-s<serial>.bin`。两种驱动各抓同一帧，用 `dm/tools/pass_dump_diff.py` 逐 pass 对比。

**结果**：54 个 pass 里，所有深度 pass（包括主深度缓冲 serial 29）两边完全一致；**第一个分歧的是 pass 008（640×360，R16F，serial 58，像素着色器 `60f3906f2280721c`）**，输入的主深度相同，输出在角色区域不同（系统驱动上角色轮廓是纯白，Turnip 上有明暗层次）。该着色器采样 4 张纹理：serial 29（主深度）、46（256×256 D16，4 层，级联阴影图，带比较）、56 和 57（3D），另外有 46 次 texel buffer fetch（常量数据，经过“无采样器 buffer 适配”和 `STORAGE_BIAS_MODULE` 改写）。下游的 pass 024、033、035（RGBA16F，serial 28）把差异放大，最终形成雾气伪影。

**下一步**：对 pass 008 的输入逐个替换/检查（texel buffer 的视图范围与对齐、3D 纹理的格式与视图、4 层阴影图的数组视图），并用 `shader-override` 逐段裁剪该着色器确认是编译器缺陷还是我们的适配问题。

## 驱动策略：Turnip 自动选择机制（现已停用，白名单为空）

由于系统驱动在 Adreno 642L 上存在渲染错误，`GraphicsDriverPolicy` 的自动模式改为：`SM7325`（API 31 及以上）使用内置 Turnip，其他 SoC 仍用系统驱动；显式选择始终优先，ADB 的 `private-vulkan*` 标记优先级更高。

自动选择 Turnip 之前先写 `files/d2r-mobile/driver-auto-pending`；首帧呈现或 Activity 正常销毁时删除。若下次启动时它仍在，说明上次没有走到首帧（崩溃或被划掉），记一次失败；**连续两次**才回退到系统驱动并持久化（`auto_turnip_failed`）。用户重新保存驱动选择会清除该状态。日志 `D2RDriver` 输出 `selection=… resolved=…`，回退时附带 `auto_fallback=1`。

| 驱动（Adreno 642L，角色选择） | 100% | 0.75 | 画面 |
| --- | ---: | ---: | --- |
| 系统驱动 | 约 12.4 FPS | 约 15.2 FPS | 雾气块状伪影 |
| Turnip（自动选择） | 约 11.0 FPS | 约 13.0 FPS | 干净 |

已验证：自动选择、首帧后清除标记、注入遗留标记后第 1 次仍用 Turnip、第 2 次回退。尚未验证：其他 SoC 的白名单（目前只有 SM7325 实测过）、在设备上真实崩溃的路径（只用 force-stop 和注入标记模拟）。

## PSO manifest 按驱动身份分文件

用户 manifest 由共用的 `pso_user.vkbin` 改为 `pso_user-<crc>.vkbin`，crc 来自厂商、设备、驱动版本、`pipelineCacheUUID` 和选项。写入只写自己的文件；读取时先读旧的 `pso_user.vkbin`（出厂种子，身份不匹配会被校验丢弃），再读自己的。实测（Adreno 642L）：Turnip 预热 120 条；切到系统驱动首次 0 条、第二次 149 条；再切回 Turnip 仍是 120 条，不再被覆盖。

## 渲染比例自动档

自动档（没有 `render-scale.txt`）对 94012 的基准是 0.75，仅在掉帧时按 0.70/0.65/0.60 下调，界面原先写成“60%–100%”已更正。Turnip 默认驱动下自动档约 13.4 FPS，画面干净。

## 去除 D2R 硬编码：Qualcomm 骨骼 UBO 降级改为结构识别

Qualcomm 系统编译器对“UBO 数组访问的动态分量索引”编译错误，原先只对两个写死的顶点着色器 key（`54c93fa22abff9ee`、`3deaf68fd65b5298`）且 `Binding 1` 的变量做降级（先读整个 vec4 再提取分量）。现在改为：Qualcomm 专有驱动上对**任何顶点着色器**中**分量索引不是常量**的 Uniform 浮点访问链做同样的精确变换；驱动常量区绑定（`kind==8`）被排除，因为后面还要审计它们的访问形状。

| 版本 | 命中的着色器 | FPS（系统驱动） |
| --- | --- | ---: |
| 写死 key | 2 个（各 48 次访问） | 约 15.4 |
| 通用，所有访问 | 32 个 | 约 12.0（变慢，已放弃） |
| **通用，仅动态分量** | **同样 2 个，各 48 次访问** | **约 15.6** |

两个目标着色器的输出与写死 key 的版本逐字节相同；转储的 111 个着色器全部通过 `spirv-val`。这条规则不依赖游戏，换成其他游戏的骨骼/蒙皮着色器会自动命中同样的模式。仍未做：其他写死的着色器 key 都是调试追踪（`DM_FRAME_DIR`、`trace_*`）和 Mali 上的深度输入实验，不影响渲染行为。

## 原生 BC 纹理（评估，未实现）

Turnip 暴露 `textureCompressionBC`（BC1/BC3/BC7 均可采样并线性过滤），系统驱动不暴露。目前后端所有 BC 纹理都在 CPU 解码成 RGBA8（体积 4–8 倍）。改用原生 BC 需要同时改格式映射、创建、上传（块行大小）、重传、缓冲到纹理拷贝（块对齐步长）、纹理到纹理拷贝和回读共约六条路径，并且需要进入游戏世界逐一验证，当前无法在设备上自动化验证，所以暂不实现。启动日志新增 `TEXTURE_COMPRESSION` 行，打印两个驱动的实际能力。

## UI / 文字清晰度：present 放大改用三次滤波

游戏的 3D、UI 和文字都以 1280×720 渲染，最后由 present 阶段用 blit 放大到面板（本机 2652×1200，约 2.07 倍），原先是双线性滤波。现在启用 `VK_EXT_filter_cubic`（系统驱动和 Turnip 都支持），源格式支持时用 `VK_FILTER_CUBIC_EXT` 放大，不支持则回退线性；`diagnostics/present-filter.txt` 写 `linear` 可关闭。日志 `PRESENT_FILTER filter=… cubic_extension=… enabled=…`。

实测（角色选择）：文字区域的平均边缘梯度 14.8 → 17.6（约 +20%），人物面部没有可见光晕或过冲，帧率无变化（约 13 FPS，blit 由硬件完成）。这只改善放大质量，不增加原始细节；要获得更高的原生文字清晰度仍需在游戏内提高 UI 输出尺寸或扩展原生 HUD 叠加层（未做）。

## 根因找到：系统驱动的雾气伪影是 Qualcomm 动态分量索引编译缺陷（已修复）

pass 008 的着色器 `60f3906f2280721c` 是**片元着色器**，里面有 16 处“UBO 数组的动态分量索引”访问，正是已知会被 Qualcomm 系统编译器错误编译的形式；之前的降级只对顶点着色器生效。把同一个精确变换扩展到顶点和片元着色器（仅对分量索引不是常量的访问链、跳过驱动常量绑定）后：

| 系统驱动，Adreno 642L | 修复前 | 修复后 |
| --- | ---: | ---: |
| 雾气伪影度量（亮度大于 120 的像素占比） | 5–13 | 0.45–0.48（Turnip 约 0.55） |
| 自动档（0.75）FPS | 约 15.5（画面错误） | 约 16.0–16.5 |
| 100% 档 FPS | 约 12.4（画面错误） | 约 12.4–13.2 |

共有 26 个着色器被改写，转储出的 99 个着色器全部通过 `spirv-val`，无 STOP。多时刻采样（5 张）度量稳定。前面所有“排除项”实验之所以无效，是因为问题出在 Qualcomm 编译器而不是我们的同步、缓存或布局。

**因此撤回“SM7325 默认 Turnip”**：系统驱动画面正确且更快（16.4 对 13.4 FPS），`GraphicsDriverPolicy` 的白名单清空，自动模式使用系统驱动；Turnip 仍可显式选择，自动回退机制保留（白名单为空时不生效）。

## 渲染槽重叠：再次评估后确定不继续（两条安全化路线都不划算）

冲突位置统计（2 槽、系统驱动、每 60 帧）：绝大部分是 `cpu_upload`，集中在 pool 5 的几个 64 KiB 桶（桶 274/294/304/314，合计约 220 MB，每帧约 5 次、约 1.9 MB），其余是若干很小的区域（pool 3/4/6 的几十到几百字节，每帧各一次）。没有 `cpu_snapshot` 类冲突。

尝试 1：冲突时不碰镜像，把客户内存拷成私有临时缓冲并绑定（顶点和索引缓冲，同一提交内按“地址+长度+脏戳”复用）。结果 7–11 FPS（比单槽慢）：绑定范围是整个缓冲区间而不是实际用到的部分，每帧仍有上百次整段拷贝，索引缓冲的实际范围又不能通过扫描 CPU 索引来推断。

尝试 2（未实现）：每个渲染槽独立的 pool 镜像。镜像驻留内存 1.1 GiB（7 个 pool，最大 744 MB），翻倍需要额外约 1.1 GiB 内存和双倍上传带宽，并且 GPU 产出的数据在槽位之间还需要同步。

GPU 有序暂存拷贝（Eden 的 upload command buffer 做法）需要在渲染 pass 之外录制拷贝；顶点缓冲在 `render_begin` 之后才读取，会拆开主 pass。三条路线都没有明确收益，已撤回全部实验代码，渲染槽保持默认 1 槽、带冲突检测的可选 2 槽（无收益）。

### 自动化驱动脚本与探索结果

`dm/tools/android_game_driver.py`：`enter <名字>` 冷启动后经 START → A → A → A → 输入名字 → 输入法候选词 → Enter 新建角色并等待进入世界（实测约 16 秒）；`explore <秒数>` 用触控摇杆做带反馈的行走（拖动后比较画面差异，被挡住就换方向，检测到整屏近黑的加载画面视为区域切换）。名字必须是输入法会原样补全的真实单词（`Warrior` 可用；`Tester2` 被补全成已存在的 `Tester`，`Qwxz` 被拆成 `Q`）。

探索结果：随机反馈行走能穿过营地栅栏的缺口到营地外围（小地图仍显示“流亡者营地”），累计约 15 分钟没有走到 Blood Moor 出口，也没有触发加载画面。过程中游戏稳定运行、无 STOP、帧率 24–30 FPS（营地外围 24–28）。战斗和区域切换仍未覆盖，需要知道出口位置的人工带路，或者给脚本加上基于小地图的寻路。

### 游戏内面板与“保存并退出”往返（adb 自动化）

世界内 `BUTTON_START` 打开背包面板，`BUTTON_R1` 切换标签页（任务日志、角色、物品栏、技能树、选项）。物品栏（装备槽、药水、卷轴、提示框）、技能树（呐喊技能页）、选项菜单（消息记录、选项、帮助、保存并退出、战利品过滤器、编年史）、任务日志均渲染正常，全程无 `STOP`，约 24–27 FPS。

选项菜单的“保存并退出”是一次完整的世界到主菜单的卸载/加载往返：黑屏过渡后回到角色列表，两个角色（Warrior、Tester）都在，存档提交 #14–#16，进程正常，无 `STOP`。这是区域切换之外能自动覆盖的最接近的场景切换。

仍未覆盖：战斗、区域切换（营地出口）、从角色列表重新进入已有角色（注入的 `BUTTON_A`、长按 A、D-pad+A、点击卡片和确认按钮都没有推进，新建角色路径可靠）。
